# Release and packaging process

## Recommended prerelease files

Publish both formats when practical:

- **ZIP** is the canonical artifact. It preserves the `.app` bundle, is simple
  to generate in CI, works well with GitHub artifact attestations and is the
  easiest file for developers to inspect.
- **DMG** gives ordinary Mac users a familiar drag-to-Applications experience.
  It is presentation, not a security feature; an unsigned or unnotarized DMG
  does not make the enclosed application trusted.
- GitHub automatically adds **Source code (zip)** and **Source code (tar.gz)**
  for the tag. Do not upload duplicate source archives manually.

For `3.3.0-intel.1`, the intended binary names are:

```text
TargetBridge-Intel-Sender-3.3.0-intel.1-x86_64.zip
TargetBridge-Intel-Sender-3.3.0-intel.1-x86_64.dmg
SHA256SUMS.txt
```

The Receiver is intentionally absent. Link users to the original TargetBridge
Receiver releases rather than repackaging a binary this fork has not changed.

## Local release candidate

```bash
TargetBridge-Sender/scripts/package_intel_sender_release.sh 3.3.0-intel.1
```

The script rebuilds the app, checks architecture, bundle identifier and code
signature, then writes ZIP, DMG and SHA-256 checksums under `dist/`. Its current
build is ad-hoc signed and suitable for controlled prerelease testing. Users may
see Gatekeeper or quarantine warnings.

## Signing and notarization boundary

A public package with a smooth first launch should eventually use:

1. an Apple Developer Program account;
2. a `Developer ID Application` certificate;
3. Hardened Runtime and reviewed entitlements;
4. Developer ID signing of the app and all nested code;
5. `notarytool submit --wait`;
6. `stapler staple` and `stapler validate` on the final app or DMG;
7. Gatekeeper validation with `spctl` on a clean Mac.

Those steps cannot be truthfully claimed by the current ad-hoc package. Do not
describe the prerelease as notarized until the exported artifact itself passes
the checks.

## GitHub prerelease checklist

1. Confirm `git status` is clean and CI passes on `intel-sender`.
2. Run the x86_64 unit suite and package script.
3. Test the packaged app, not only the Xcode product, on the validated Intel Mac.
4. Verify first launch, Screen Recording, connect/disconnect, 2048 x 1152,
   2304 x 1296, H.264, HEVC, menu controls, login behavior and uninstall.
5. Review [release notes](Release-3.3.0-intel.1.md) and known limitations.
6. Tag the exact commit as `v3.3.0-intel.1`.
7. Create a GitHub **prerelease**, attach ZIP, DMG and checksums, and allow GitHub
   to provide the two source archives.
8. Verify checksums and, when generated by CI, the GitHub artifact attestations.
9. Keep the release marked prerelease until a downloaded artifact has completed
   the same end-to-end test as the local package.

## Versioning

The `-intel.N` suffix makes the fork lineage and maturity visible without
pretending to be the upstream release. Increase `N` for fork prereleases based
on the same upstream version. Use a new semantic base only when the inherited
base changes or the fork intentionally establishes its own version line.
